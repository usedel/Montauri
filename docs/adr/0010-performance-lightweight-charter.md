# ADR-0010: 产品定位转向「高性能 · 轻量」，性能与体积升为一等目标

- 状态：**已定案**
- 日期：2026-10-05
- 决策者：产品负责人裁决
- 上游：`docs/python_ide_tech_plan_v3.md` v3.1 §1 / `docs/python_ide_dev_plan_v2.md` v2.1 §1.1
- 落地：`.codebuddy/rules/architecture/RULE.mdc` · `AGENTS.md`（内联铁律）· `README.md` · `ci/budgets.toml`（既有，不改）· `docs/tech-debt.md` TD-025（复审清单）

## 背景

项目自立项起的定位一直是「**单人自用** Python IDE」，这个定位不只出现在标题里，它**作为论据**支撑了 60+ 处决策：Inter 字体走系统栈（跨机一致性收益为零）、nightly 只告警不阻断（没人盯 CI）、更新通道延后、插件硬沙箱不立项（收益对自用场景有限）、Watches 存 localStorage（无跨设备诉求）、SSRF 不拦只提示（自用工具知情即可）等。

2026-10-05 产品定位变更：OpenCharm 不再是「自用工具」，而是**高性能 · 轻量 Python IDE**。由此产生三个必须立刻回答的问题：

1. 「自用」这一定位失效后，上述以它为论据的历史裁决是否仍成立？
2. 「高性能 · 轻量」如果只是文案，不会产生任何约束力；要如何让它进入日常决策？
3. 是否要顺势收紧性能红线（内存 / 冷启动 / 体积）并把门禁从「只告警」升级为「阻断」？

可选的三个范围（A 定位真源 + 性能章程 / B 只改文案 / C 全量替换 + 历史复审）已由产品负责人裁决为 **A**，并附带两个限定：**目标用户画像不变**、**性能红线先定性不定数字**。

## 决策

1. **产品定位**：面向「FastAPI + 爬虫 + 小脚本」开发者的**高性能 · 轻量 Python IDE**；原「单人自用」定位作废。
2. **目标用户画像不变**：仍是 FastAPI + 爬虫 + 小脚本。因此既有功能裁决（FastAPI 优先、Django 浅做、不做 pytest 面板 / Jupyter / Scientific 模式 / 通用多语言）**继续成立**，本轮不复议。
3. **性能与体积升为一等目标**，与功能正确性同权，写入架构铁律（`RULE.mdc`「性能与轻量（一等目标，不可违反）」+ `AGENTS.md` 内联全文），约束条款四条：
   - **预算先行**：任何功能不得突破 `ci/budgets.toml` 的预算（巨型文件行数 / 命令面 / 产物体积）与项目级性能指标（数值真源 `python_ide_dev_plan_v2.md` §1.2）；调整数值必须显式 PR 写清理由，脚本绝不自动抬阈值；
   - **默认轻量**：新增依赖、常驻进程、后台轮询/定时器先问「能不能不做 / 能不能按需加载」，按需加载优先于常驻；
   - **运行时开销红线**：`probe` 采样 < 1.5x（当前 1.35x），改采集路径必须 bench 回归；
   - **体积与内存是卖点不是技术细节**：突破预算的功能要么换做法，要么不立项，**不允许「先上线再优化」**。
4. **数值维持现值不动**：冷启动 < 1.5 s、空闲内存 ≤ 600 MB、探针开销 < 1.5x、`budgets.toml` 各项上限——本轮**不收紧也不放宽**。理由是方向刚变更、实测基线未刷新，拍新数字等于拍脑袋；等方向稳定 + 拿到新实测再谈。
5. **门禁策略本轮不改**：nightly 的 bench / budget job 仍是 `continue-on-error`（只告警不阻断）。是否升级为 PR 阻断项留待方向稳定后单独决策。
6. **历史「自用」论据不做逐个复审**：仅登记 `docs/tech-debt.md` **TD-025** 复审清单（含条目、原论据、失效原因、复审时机），由后续独立 PR 处理。

## 备选方案

| 方案 | 评估 | 结论 |
|---|---|---|
| B · 只替换 5 处定位文案 | 最快，但方向不产生任何约束力：定位写着「高性能轻量」，实际仍可随时突破预算 | ❌ 否决 |
| C · 全量替换 60+ 处表述 + 逐个复审历史裁决 | 最彻底，但工作量多日；且画像不变使多数裁决（FastAPI 优先、不做 pytest/Jupyter）本身仍成立，复审收益集中在少数几项 | ❌ 本轮否决（降级为 TD-025 复审清单） |
| 收紧数字（内存 ≤400 MB / 冷启动 <1 s / 产物 ≤5 MB）+ 门禁升级为阻断 | 硬约束力最强，但当前实测 420~600 MB，收紧后**当场不达标**，门禁会立刻全红并逼出「抬阈值」的反向动作 | ❌ 否决（先定性，等新实测） |
| **A · 定位真源 + 性能章程（定性）** | 定位统一、约束进铁律、数值与门禁不动，既不冒无法达标的风险，也让新方向立刻进入日常决策 | ✅ **选定** |

## 后果

- **正面**：
  - 「性能与轻量」从口号变成**可引用的规则**：PR 评审可以直接引用本 ADR 与 `RULE.mdc` 条款驳回「先上线再优化」的提案。
  - 画像不变，功能路线零扰动，本轮改动面收在 5 份定位真源 + 1 份 ADR + 1 条技术债。
- **负面 / 取舍**：
  - 本轮**不产生新的硬门禁**：约束目前靠评审自觉 + nightly 告警，缺少「CI 直接拦」的牙齿；这是**已知且接受**的取舍（见决策 5）。
  - 历史文档（调研报告、UI 设计报告、roadmap 等）仍留有「自用」表述与原论据，**与现行定位不一致**是本 ADR 有意为之的延迟处理，读这些文档时必须记住「论据已过期，结论可能仍成立」——清单见 TD-025。
- **约束**：
  - 后续任何「调阈值」的 PR 必须在描述里说明为什么必须突破预算；`budget-check.mjs` 保持绝不自动抬阈值。
  - 若将来方向稳定并决定收紧数字或升级门禁，**新开 ADR 取代本条**（不就地改写，保留本决策的时间戳与理由）。
  - `probe` 开销红线（< 1.5x）与 Python 规范红线同款，改采集路径的 bench 回归义务不因本 ADR 变化。
