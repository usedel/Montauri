# Montauri：低延迟编辑预测 研究方案

> 版本：v0.1 · 日期：2026-09-15 · 状态：**探索中**（采集器已埋点，待真实数据驱动决策）
> 关联文档：`python_ide_tech_plan_v3.md`（外壳/三层补全）· `python_ide_dev_plan_v2.md`（Phase 4 打磨期）· `data-directory-layout-v2.md`（数据目录）
> 定位：**研究/探索方案**，非正式开发计划（`python_ide_dev_plan_v2.md` 才是排期与执行的唯一依据）。本文固化「低延迟编辑预测」的方向论证、数据契约与决策流程，供数据攒足后据此决定是否立项、如何立项。

## 1. 定位与目标

**目标形态**：Cursor 式「整行 / 多 token 灰字预测」（ghost text / inline completion）——光标后灰字显示预测的代码片段，`Tab` 接受。

**核心约束**：Cursor 靠本地大模型实现，违背本项目「轻量」原则（内存红线 ≤ 600 MB、逐键 < 30 ms 无感，见 `python_ide_tech_plan_v3.md`）。本方案要回答：**能否用本地结构化信号替代通用参数，达到单人自用场景满意的预测效果。**

**与现有补全的区别**：现有三层补全（模板 `0xx` / 运行时 `1xx` / 静态 `2xx`）是**下拉列表**式，粒度是单标识符/属性/键；本方案是**灰字 inline**，粒度是整行 / 多 token。

---

## 2. 为什么「轻量」能替代大模型（核心论证）

大模型的价值是**覆盖面**（任何语境都给个像样的续写）；而项目的真实分布是低熵的：

- 单人自用：「你 + 你的项目」这一个分布；
- 领域固定：FastAPI 路由 / 爬虫解析 / 小脚本，模式高度重复；
- 单行内：上一行写完，下一行大概率是它的变体。

因此命题转化为：**能不能在小分布上，用「结构化本地信号」打到大分布的效果。** 结论是能，且有 LLM 都没有的两张牌：

1. **运行时 trace 的确定性语义**（`montauri-intel` 已知道 `o` 的运行时类型与 shape，属观测事实而非统计猜测）；
2. **逐键预算 < 30 ms 的内存化索引**（`TraceIndex` 已全量载入内存、纯函数、无进程往返）。

## 3. 方法空间（五类，按信号来源）

| 方法 | 数据/信号 | 参数 | 延迟 | 覆盖面 | 是否撞红线 |
|---|---|---|---|---|---|
| ① 语法/规则驱动 | Python 语法 + 类型 | 零 | <1ms | 窄而准 | 否 |
| ② 统计 n-gram（序列预测） | 编辑历史/trace 调用序列 | 极小 | <5ms | 中（重复场景） | 否 |
| ③ 检索/CopyPaste | 代码库快照 | 零 | <10ms | 中 | 否 |
| ④ 本地小模型 SLM | 预训练权重 | 百万~数十亿 | 50ms~500ms | 宽而泛 | **是** |
| ⑤ 混合级联 | 以上串联 | — | 按需 | 视设计 | 看设计 |

**小模型（④）的诚实评估**：1~3B code LM 撞内存红线 + 秒级延迟；<500M 蒸馏模型效果断崖且要引入推理运行时。**只作为级联最后一个 optional tier，不作底座。**

## 4. 关键技术判断（决策依据）

1. **Ghost text 的「可拒绝性」是轻量方案的护城河**：错误的灰字比没有更糟（打断心流）。轻量方法可带显式置信度，**宁缺毋滥**；大模型却必须硬给答案。战场从「覆盖率」转移到「高置信片段的覆盖率」。

2. **整行是检索式方案最擅长的粒度**：整行预测 ≈ 「上一行 + 当前行前缀」语境下，**回放一条曾写过/运行过的最相似的整行**。整行高重复、命中即高置信、未命中即拒绝，几乎无「半对半错」中间态。

3. **行中补全 > 从零整行（实测信号）**：给定前 50% 字符的「行中补全」精确率远高于空行首凭空预测整行。工程重心应放在**行中多 token 补全**，从零整行作为低优先级补充。

4. **低延迟预测索引必须进程内，不走 LSP 桥**：下拉补全可接受 `200 ms 去抖 + LSP 往返`；灰字预测逐键 + 无感（< 30 ms），`intel` 是独立 LSP 进程、IPC 往返即可能掉帧。整行预测索引（编辑历史 + 语法骨架）应作为**编辑器进程内新前端模块**，数据启动时载入内存、永不跨 IPC；intel 的 trace 仅由低频快照提供类型真相。

## 5. 目标架构（三级级联 + 置信度门控）

```
击键
 └─ Tier 0（<1ms，纯前端语法）     缩进/block 骨架/闭合符号 → 确定性，必出
    └─ 拒绝 →
      Tier 1（1~10ms，intel 内存） 类型驱动的整链成员 + 访问模式回放 → 高置信
       └─ 拒绝 →
        Tier 2（10~50ms，本地索引） 编辑历史行对回放 → 中置信
         └─ 拒绝 →
          （可选）Tier 3 后台小模型，仅显式等待时用 → 撞内存，先不做
```

每层一个置信度阈值，不够则向上 / 直接拒绝（不出灰字）。

## 6. 数据采集（契约已锁定，V1）

### 6.1 契约字段（`EditEvent`，JSONL 一行一条）

| 字段 | 类型 | 含义 |
|---|---|---|
| `ts` | i64 | 毫秒时间戳（后续新鲜度加权） |
| `lang` | string | 固定 `"python"`（其他语言不采） |
| `indent` | u32 | 本行前导空白字符数（预测时复现缩进） |
| `prev` | string\|null | 上一非空行净内容（向上回看 ≤ 5 行内最近非空行；无则 null） |
| `line` | string | 本行净内容（去首尾空白） |

### 6.2 采集规则

- **只采 python**；仅「光标离开 + 该行自上次定型后被编辑过（dirty）」才采——方向键上下浏览不产生噪音（数据质量底线：垃圾进垃圾出）。
- **逐条 invoke**（频率 ≈「每行一次」，远低于逐键），无缓冲丢失问题；采集失败静默降级，绝不干扰编辑主流程。
- **跨项目聚合**（不落 `project_hash`）：学的是「用户本人」的写法，同一习惯跨工作区复用。
- **已知覆盖缺口**：一行若「写完直接 Ctrl+S / 关文件 / 切换标签页、光标未离开」V1 不采（切 tab 会重置采集状态而丢弃未定型行）；后续可加「保存/切 tab 时冲刷 dirty 行」补齐。

### 6.3 存储

`<data_root>/edit_history/events.jsonl`，超 8 MiB 轮转 `events.1.jsonl`（数据目录约定见 `data-directory-layout-v2.md`，已登记）。

## 7. 数据驱动决策流程

数据攒足（建议 2~4 周）后，跑统计脚本量化「可预测性地板」：

```powershell
python -u tools/edit_history_stats.py --jsonl %LOCALAPPDATA%\Montauri\edit_history\events.jsonl
```

关键指标：**覆盖率**（prev 有历史可查的比例）、**行中补全精确率**（前缀 50% 字符）、**整行 top-1 / top-K 精确率**、**行对复现频次分布**。

### 代理数据 Demo（非结论，`bench/sample` 101 文件混切，跨文件噪音稀释）

| 指标 | 值 |
|---|---|
| 覆盖率 | 28.8% |
| 整行回放 top-1 精确 | 36.2% |
| 整行回放 top-5 精确 | 42.7% |
| **行中补全精确率（前 50% 字符）** | **87.3%** |
| 行对 ≥2 次比例 | 5.3% |

> ⚠ 这是「成品代码 + 多项目混杂」代理，仅验证脚本工具链正确 + 展示「行中补全」上限诱人；真实单用户数据重复率会更高、但编辑流噪声会拉低，**真数字以 JSONL 为准**。

### 判定阈值（待真实验证后据此立项）

| 真实数据结果 | 决策 |
|---|---|
| 行中补全精确率 **≥ 80%** | Tier 2 行对回放成立，**SLM 永久不做** |
| 行中补全精确率 **20%~80%** | 先上 Tier 0/1/2 级联，保留 Tier 3 评估 |
| 行中补全精确率 **< 20%** | 回退重新评估小模型路线 |

## 10.1 灰字与下拉共存实证（2026-10-14，FUSION-1 探针副产品）

**背景**：FUSION-1（实参位变量补全）真机反馈暴露了 Monaco 0.52 inline/suggest 协同的多个边界（详见 `arg_var_fusion_dev_plan.md` §0/§10）。其中「suggest preview 在 autoClosingBrackets 空前缀场景被 lineSuffix 吞」一度引发「灰字在下拉打开时无法显示」的担忧——但**编辑预测走的是 augmentation 通道，结论恰好相反**：

| 通道 | 语义 | 实测状态 | 对编辑预测的意义 |
|---|---|---|---|
| 自研 inline provider（与选中项**相等**） | 与下拉重复的候选 | 下拉打开时被双池语义压制（`inlineCompletionsSource.js:44`） | 无关——预测内容不与下拉候选重复 |
| suggest preview（选中项剩余部分） | 下拉选中项的内联预览 | 空前缀+`)` lineSuffix 场景不渲染；带前缀时正常 | 无关 |
| **augmentation**（inline 项 = 选中项的**扩展**） | 下拉选中项 + 灰字续写扩展部分 | **✅ 带前缀实测渲染**（如输入 `c` 后）；⚠️ 空前缀瞬间（刚打 `(`）**provider 不被引擎调用**（PROBE-EMPTY-AUG 实证，onDidType trigger 被 suggest 分支旁路） | **编辑预测的主通道**：预测永远以「用户已选/已输入内容为前缀续写」，天然满足 `singleTextEditAugments` 的扩展语义；空前缀灰字缺席不伤体验（下拉刚弹出，注意力在下拉上） |

**探针实证**（e2e 真实 pyrefly 桥，`ghost-text-decoration-preview=>, timeout=10` 同时与 `ghost-text-decoration=>b_url` 双灰字并存）：

- 下拉打开 + 选中项存在 + inline 项扩展选中项 → 引擎 `_computeAugmentation`（`inlineCompletionsModel.js:161-176`）把扩展部分渲染为 `ghost-text-decoration-preview` 类灰字——**这正是 VS Code 里 Copilot 灰字与下拉共存同一个机制**；
- 也就是说：**编辑预测的灰字不会遇到 FUSION-1 的任何一条死路**。预测的形态（续写用户已输入内容）天然是「扩展」而非「相等」；Tab 语义在 augmentation 分支由引擎统一处理（接受下拉选中项 + 扩展一起写入）。

**对 §5 架构的增量结论**：

1. Tier 0-2 的输出只要满足「以当前 word/选中项为前缀」即可在两种状态（下拉开/关）下都正确显示——下拉关时走普通 ghost（FUSION-1 GHOST-ISO 已证），下拉开时走 augmentation（本节实证）；
2. 基础设施零新增：inlineCompletions contribution 已在 `monaco.ts`（FUSION-1 引入），provider 注册模式、依赖注入防环、dev 钩子全套可复用；
3. 一个新注意点：预测项与下拉选中项**相等**时（用户刚从下拉选了个词、预测内容恰好也是它）会被双池压制——无害，引擎自动处理（显示零扩展 = 无灰字，正确行为）。

**结论**：UX 冲突风险关闭，编辑预测的呈现层路径全部打通。剩余不确定性只在**预测质量**（§7 数据驱动决策），那是立项门槛本身。
