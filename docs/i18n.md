| 层 | 状态 | 说明 |
|---|---|---|

| 顶部菜单项 | ✅ 已纳管 | `main.ts::getMenuItems` 68 条 label 走 `t()`；切换语言时展开中的菜单就地重绘 |

| Toast / 对话框按钮 | 🟡 部分 | 组件自身文案（关闭通知等）已纳管；**调用点传入的文案**仍是中文硬编码 |
| 文件树 / Git / 调试面板等动态文案 | ⬜ 未纳管 | 约 3500+ 处仍为中文硬编码，见「后续」 |

设计前提：**默认语言 = 简体中文**。项目 `__tests__` 里有大量以中文文案做断言的用例，
默认语言保持中文 = 存量断言零改动即可继续通过。英文由用户主动切换触发。

## 架构

```
shell/src/i18n/
├── index.ts             运行时：getLocale / setLocale / t / applyDomI18n / onLocaleChange
├── backendError.ts      后端错误翻译层（模板匹配 + 参数回填）
└── locales/
    ├── zh-CN.ts         真源；导出 TKey（keyof typeof zhCN）
    └── en-US.ts         Record<TKey, string> —— 漏译/多译/拼错在 tsc 阶段报错
```

- **扁平 key**（`menubar.file`）而非嵌套对象：`search.searchScope` 这类「既是叶子又是分支」的
  key 在嵌套结构里无法表达；扁平化后「漏译检查」退化为 key 集合运算。
- **DOM 标记**：`data-i18n`（文本）/ `-tip`（data-tip）/ `-aria`（aria-label）/ `-ph`（placeholder）/
  `-title`（title）/ `-alt`（alt）。`applyDomI18n()` 扫描并就地改写，写文本时只替换**直接子文本
  节点**，图标 `<i class="codicon">` 不会被抹掉。
- **语言存 `localStorage`**（键 `opencharm.locale`），不进 `settings.json`：语言是本机壳偏好，
  与工作区无关；进 Settings 会牵动 Rust `Settings` 的三处同步义务（见 `state.ts` 相关注释）。
- **动态内容**由各域模块订阅 `onLocaleChange` 自行重绘（菜单已在 `menuBar.ts` 实现）。

## 新增文案：三步

1. **静态 HTML**：直接写中文，跑 `python3 tools/i18n/extract_html.py` 自动打 `data-i18n*` 标记并
   导出词条；再在 `tools/i18n/data/en_*.json` 补英文。
2. **TS 动态文案**：在 `tools/i18n/data/manual_zh.json` 登记「key → 中文」，在同目录 `en_*.json`
   补英文，代码里写 `t("your.key")`。
3. 跑 `python3 tools/i18n/gen_locales.py` 重新生成语言包（会校验中英文 key 一一对应）。

然后 `npx tsc --noEmit` —— 英文漏了会直接编译报错。

## 新增语言

1. 建 `src/i18n/locales/<id>.ts`，`export const xxYY: Record<TKey, string> = {…}`；
2. 在 `index.ts` 的 `Locale` 联合类型、`PACKS`、`LOCALE_OPTIONS` 三处登记；
3. 在 `index.html` 的语言下拉加一个 `<option>`。

## 后端错误

Rust 文案不动，前端按「中文模板 → 英文模板」匹配（`backendError.ts`）。Rust 侧改了错误文案而
映射表没跟上时，`python3 tools/i18n/scan_rust.py` 会报未登记条目（退出码 1）——建议接入 CI。
未命中模板时**原样返回中文**（宁可露原文，也不吞掉错误）。

## 后续（按优先级）

   等约 3500 处）——建议按功能域分批抽，每批抽完同步把测试断言改成 `t(key)`。
2. 日期 / 数字 / 复数（目前只做字符串替换，未接 `Intl`）。
3. 英文文案带来的布局回归（英文普遍比中文长 30%~60%，按钮与侧栏宽度需过一轮视觉检查）。
